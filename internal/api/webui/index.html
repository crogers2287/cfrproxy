Smart router — auto

How a request addressed to auto is placed

1. Grade the request. The classifier model answers one word — routine, careful or hard. cfrproxy measures the rest itself: prompt size, conversation depth, tool count, whether an image is attached. Nothing in that profile names a model, so it never goes stale when your models change.

2. Walk the tier's list, in the order you wrote it. Put local models first. Each entry is checked against live facts: is it served, is it loaded in llama-swap (warm), does it have a free slot, is its context window big enough, can it see images, and how often has it failed in the last 3 days. Entries can be provider/model, a pool name, or a glob like fred/*flash-next* — a renamed or unloaded model simply drops out instead of breaking the route.

3. First entry that passes wins. A model that is merely busy, cold or unhealthy is kept as a last resort in that order — loading a cold model costs minutes, so a warm cloud model beats it. A conversation stays on the model it started on (sticky) until that model can no longer take it, e.g. it outgrew the local window.

The chosen route shows in Live traces as auto→careful→fred/ornith. Every decision is also appended to ~/.cfrproxy/route-decisions.jsonl.

Providers

Where requests actually go, and how priority works

A provider is one upstream API: a local llama-swap or Ollama, a cloud key, or a subscription bridge. Address one directly with provider-name/model. A bare model name goes to the first enabled provider by priority that lists it (drag cards, or use ↑ ↓ on a phone); a name nobody lists goes to the top provider's default model. Each card shows its default model, aliases, pinned models, context override and thinking level. Test sends a one-token request.

Model map

stage 1 — rename before routing
Rewrite the names harnesses insist on

Some harnesses hard-code model names. Map those names to any provider/model — e.g. claude-opus*, claude-sonnet*, claude-haiku* so Claude Code's built-in presets become switchable slots, or gpt-4o → auto so an old tool gets the smart router. Patterns are an exact name or a trailing *. The rewrite happens before anything else on this page.

Fallback chain

The safety net for every model, stage 4

If the model a request resolved to can't serve — quota exhausted, rate limited, overloaded, unreachable, or the prompt overflows its context — the request continues down this list instead of failing. Order matters: the first target that answers wins, and the reply carries a ⚠️ notice saying what was skipped. Up to 5 targets are tried. This applies to every route, including what the smart router picked. Share endpoints can opt out ("disable fallback") so a key you hand out cannot spend on providers its owner was never granted.

Named routers — auto:NAME

A separate routing setup you can hand to one harness or one share endpoint

Each named router has its own classifier and a fixed model per task bucket (the legacy bucket style; they do not use smart mode). Address one as auto:NAME, or auto-plan:NAME when it has a planner. Typical use: a share endpoint whose forced model is auto:budget, so a guest gets a cheap setup while your own auto stays local-first.

Fusions — fusion, fusion:NAME

Several models answer, one judge writes the final reply

A fusion sends the same prompt to 2–4 participant models in parallel, then a judge model synthesizes one answer from their drafts. Slower and pricier than a single call — reserve it for hard questions. It returns one ordinary answer, so it can sit anywhere a model can: a tier above, a share endpoint's forced model, a provider default. fusion is the default panel configured here; named panels are addressed as fusion:NAME. Point a harness at /p/cfrproxy-fusion/v1 for a provider whose whole catalogue is your fusions.

Sessions & sub-agents

live · a session is one harness run; its main agent, sub-agents, hooks and searches appear as they start
How to read it

Claude Code stamps every request of one CLI run with a session id, so the main agent and everything it spawns (Task sub-agents, hooks such as the security monitor, WebSearch sub-requests) group under one card. Each row is one conversation: its role, where the router sent it, turns so far, cache hit on the last turn, and whether a request is running right now (the proxy publishes a start marker before forwarding). A sub-agent that keeps showing miss or low cache on its first turn is one whose head has not been seeded yet; the router seeds it after that turn.

Consensus round table

Define agent profiles — each a persona pinned to a model — and let them deliberate a question together. Any MCP-capable agent (Claude Code, etc.) can convene the panel as a tool.

Synthesizethe moderator merges into consensus + dissent

Context compression

Summarize old turns past a threshold

When a request exceeds the threshold, older turns are summarized by the summarizer model and replaced with one compressed block; recent turns stay verbatim and summaries are cached per conversation prefix. The trace note shows compressed ~A→~B tok.
